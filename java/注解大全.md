## @Override

首先需要明确一个小误区： **`@Override` 并不是 Spring Boot 框架特有的注解** ，而是 **Java 语言自带的核心注解** （从 Java 5 开始引入）。

不过，因为 Spring Boot 是基于 Java 的框架，并且大量使用了面向接口编程的思想，所以你在开发 Spring Boot 项目时会非常频繁地看到它。

在 Spring Boot（以及所有 Java 程序）中， `@Override` 的主要作用可以总结为以下两点：

### 1\. 编译期安全检查（最核心的作用）

`@Override` 告诉 Java 编译器：“下面这个方法，我打算 **重写（Override）父类的方法** ，或者 **实现（Implement）接口中的方法** ”。

编译器看到这个注解后，会去父类或接口中检查是否存在签名（方法名、参数类型和个数）完全一样的方法。

- **如果存在** ：编译顺利通过。
- **如果不存在** （比如你把方法名拼写错了，或者参数写错了）：编译器会立刻 **报错** ，阻止程序运行。

**举个例子：** 假设你想在 Spring Boot 启动时执行一段代码，你会实现 `CommandLineRunner` 接口。它的正确方法名是 `run` 。

```
@Component
public class MyRunner implements CommandLineRunner {
    
    // 如果没有 @Override，如果你不小心把 run 拼成了 ran
    // 编译器不会报错，它会认为你只是写了一个新的普通方法叫做 ran()。
    // 结果就是你的代码在启动时根本不会执行，这种 Bug 很难排查。
    
    @Override
    public void run(String... args) throws Exception {
        // 加上 @Override 后，如果你拼成了 ran，编译器会直接标红报错：
        // "Method does not override method from its superclass"
        System.out.println("Spring Boot 启动啦！");
    }
}
```

### 2\. 提高代码的可读性和维护性

在复杂的 Spring Boot 项目中，类与类之间的继承关系或接口实现关系可能非常复杂。 加上 `@Override` 相当于给其他开发者（或者几个月后的你自己）贴了一个显眼的标签： **“这个方法不是我凭空创造的，它是来自上面（父类或接口）的规范要求。”**

### Spring Boot 中的常见使用场景

在日常的 Spring Boot 开发中，你通常会在以下场景高频使用 `@Override` ：

- **编写 Service 层时** ：通常我们会先定义一个接口，再写实现类。
	``` java
	public interface UserService {
	    User getUserById(Long id);
	}
	@Service
	public class UserServiceImpl implements UserService {
	    @Override // 必须实现接口规定的方法
	    public User getUserById(Long id) {
	        return userRepository.findById(id).orElse(null);
	    }
	}
	```
- **配置 Spring 框架组件时** ：比如实现 `WebMvcConfigurer` 来配置跨域或拦截器。
	``` java
	@Configuration
	public class WebConfig implements WebMvcConfigurer {
	    @Override
	    public void addInterceptors(InterceptorRegistry registry) {
	        // 添加自定义拦截器
	    }
	}
	```

**总结：** `@Override` 就像是一个 **语法保险** 和 **路标** 。它不改变代码的实际运行逻辑，但能帮你把拼写错误扼杀在摇篮里，并让代码结构一目了然。在 Spring Boot 开发中，只要你是在重写或实现方法， **强烈建议永远加上它** 。

在Spring Boot开发中，以下四个注解是非常核心且高频使用的，主要负责构建 RESTful API 和进行安全权限控制。以下是它们的具体作用和使用场景：

##  @RestController (REST控制器)

- **作用：** 这是一个组合注解，本质上是 `@Controller` 和 `@ResponseBody` 的结合体。它告诉Spring这个类是一个负责处理HTTP请求的控制器，并且该类中所有方法的返回值都应该直接写入HTTP响应体（Response Body）中。
- **特点：** 当你使用这个注解时，Spring会自动将方法返回的对象（如实体类、Map或List）序列化为 **JSON 或 XML** 格式返回给前端，而不是去寻找一个对应的HTML视图（View）页面。
- **位置：** 只能用在 **类** 上。

## @RequestMapping (请求映射)

- **作用：** 用于将特定的 Web 请求（URL 路径）映射到具体的类或方法上。你可以用它来指定路径（ `path` ）、HTTP请求方法（GET、POST等）、请求头（ `headers` ）等。
- **特点：** 虽然可以用在方法上，但在现代Spring Boot开发中，它最常被用在 **类级别** ，用来为整个控制器提取一个 **公共的根路由（Base URL）** 。
- **位置：** 可用在 **类** 或 **方法** 上。

## @GetMapping (GET请求映射)

- **作用：** 它是 `@RequestMapping(method = RequestMethod.GET)` 的快捷派生注解。专门用于将 HTTP **GET** 请求映射到特定的处理方法上。
- **特点：** 语义非常明确，通常用于从服务器 **查询或获取数据** （例如获取用户信息、加载列表等），不应该用于修改数据的操作。
- **位置：** 只能用在 **方法** 上。

## @PreAuthorize (方法级前置权限校验)

- **作用：** 这是 Spring Security 提供的一个注解，用于在方法执行 **之前** 进行权限拦截和验证。
- **特点：** 它支持强大的 **SpEL（Spring 表达式语言）** 。你可以编写表达式来判断当前发起请求的用户是否拥有特定的角色（Role）或权限（Permission）。如果表达式计算结果为 `false` ，Spring Security 会直接拦截请求并抛出 `AccessDeniedException` （通常前端会收到 403 Forbidden 状态码），业务方法 **不会被执行** 。
- **位置：** 可用在 **类** 或 **方法** 上（通常用在方法上以实现细粒度控制）。

### 综合示例：它们如何协同工作？

为了更直观地理解，我们可以看一个将这四个注解结合在一起使用的典型代码示例：

``` java
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;

// 1. 声明这是一个REST API控制器，返回的数据会自动转为JSON
@RestController 
// 2. 声明该类下所有路由的基础路径都是 "/api/users"
@RequestMapping("/api/users") 
public class UserController {

    // 3. 处理具体的GET请求，最终路由为: GET /api/users/{id}
    @GetMapping("/{id}") 
    // 4. 权限校验：只有拥有 'ADMIN' 角色的用户才能调用这个方法
    @PreAuthorize("hasRole('ADMIN')") 
    public UserInfo getUserDetail(@PathVariable Long id) {
        
        // 如果当前用户不是ADMIN，代码根本不会执行到这里
        UserInfo user = new UserInfo(id, "JohnDoe");
        
        // 直接返回对象，@RestController会将其转为 {"id": 1, "name": "JohnDoe"}
        return user; 
    }
}
```

## @Controller (传统控制器)

- **作用：** 它是 Spring MVC 中的核心注解，用来标记一个类为专门处理 Web 请求的组件（控制器）。
- **特点：** 默认情况下，被 `@Controller` 标记的类中的方法，其 **返回值会被解析为“视图名称”（View Name）** 。也就是说，Spring 会拿到这个返回值（通常是个字符串），去寻找对应的 HTML、Thymeleaf 或 JSP 模板文件，然后把渲染好的页面返回给用户。
- **适用场景：** 传统的“前后端不分离”项目，即后端不仅要处理数据，还要负责返回完整的网页。
- **位置：** 只能用在 **类** 上。

## @ResponseBody (响应体绑定)

- **作用：** 它的作用是打破 `@Controller` 的默认行为。它告诉 Spring：“ **请把这个方法的返回值直接塞进 HTTP 响应体（Response Body）里，不要去当成视图名称解析了！** ”
- **特点：** 当 Spring 看到这个注解时，会调用底层的消息转换器（ `HttpMessageConverter` ，通常是 Jackson），自动将你返回的 Java 对象（如实体类、Map、List）序列化为 **JSON 或 XML** 格式的数据。
- **适用场景：** 现代的“前后端分离”项目（提供 [^1]RESTful API）、[^2]AJAX 请求响应。
- **位置：** 可以用在 **方法** 上（仅对该方法生效），也可以用在 **类** 上（对该类中所有方法生效）。

### 核心联系：为什么会有 @RestController？

在前后端分离架构流行之前，大家都是用 `@Controller` 返回页面。后来大家都开始写 API 返回 JSON，于是代码变成了这样：

``` java
@Controller
public class MyApi {
    
    @RequestMapping("/data1")
    @ResponseBody // 每个方法都要加，很繁琐
    public Map getData1() { ... }

    @RequestMapping("/data2")
    @ResponseBody // 每个方法都要加，很繁琐
    public Map getData2() { ... }
}
```

为了偷懒和让代码更简洁，Spring 4.0 引入了 `@RestController` 。 **`@RestController` 的源码里就包含了 `@Controller` 和 `@ResponseBody`** ，所以你只需要在类上加一个 `@RestController` ，里面的所有方法就默认都会把返回值当成 JSON 丢给前端了。

### 直观的代码对比示例

为了让你彻底明白，我们来看两种不同的写法及其结果：

#### 场景 A：只用 @Controller (返回页面)

```java
@Controller
public class WebPageController {

    @GetMapping("/home")
    public String showHomePage() {
        // Spring 会去试图寻找名为 "home.html" 或 "home.jsp" 的模板文件
        // 如果找不到，会报 404 错误
        return "home"; 
    }
}
```

#### 场景 B：@Controller 配合 @ResponseBody (返回数据)

```java
@Controller
public class ApiController {

    @GetMapping("/user")
    @ResponseBody // 加上这个，Spring 就不去找模板了
    public User getUserInfo() {
        User user = new User("Alice", 25);
        // Spring 会将返回的 user 对象转成 JSON: {"name": "Alice", "age": 25}
        // 直接在浏览器中显示这段 JSON 数据
        return user; 
    }
}
```

[^1]: ###  什么是 RESTful API？
	
	RESTful API（Representational State Transfer，表现层状态转换）是一种软件架构风格，用于设计网络应用程序的接口。它强调用**标准、统一**的方式来管理网络上的“资源”。
	
	**RESTful API 的四大核心原则：**
	
	1. **一切皆资源 (Resources)：** 服务器上的所有数据（如用户、文章、商品）都被视为“资源”，每个资源都有一个唯一的网址（URL）来定位。例如：`https://api.website.com/users`。
	    
	2. **使用标准 HTTP 方法 (Verbs)：** 客户端通过不同的 HTTP 动词告诉服务器要执行什么操作：
	    
	    - **GET**：获取资源（例：查询用户列表）。
	        
	    - **POST**：创建新资源（例：注册新用户）。
	        
	    - **PUT / PATCH**：更新资源（例：修改用户资料）。
	        
	    - **DELETE**：删除资源（例：注销账号）。
	        
	3. **无状态 (Stateless)：** 服务器不会保存客户端的会话状态。每次客户端发请求，都必须自带所有必要的信息（如身份验证的 Token），服务器处理完就结束，不留记忆。
	    
	4. **返回标准格式 (JSON)：** 服务器通常以 JSON（JavaScript Object Notation）格式将数据返回给客户端，因为这种格式轻量且易于各类编程语言解析。

[^2]: ### 什么是 AJAX 请求与响应？
	
	AJAX（Asynchronous JavaScript and XML，异步 JavaScript 和 XML）是一种在无需重新加载整个网页的情况下，能够更新部分网页的技术。
	
	_(注：虽然名字里有 XML，但现在绝大多数 AJAX 请求交互使用的数据格式都是 JSON)_
	
	**AJAX 的工作流程：**
	
	1. **触发事件：** 用户在页面上进行某个操作（如点击“加载更多”按钮、填写完表单失去焦点）。
	
	2. **发送请求 (Request)：** 浏览器中的 JavaScript 代码（通过 `XMLHttpRequest` 或更现代的 `fetch` API）在后台偷偷向服务器发送一个网络请求。**这个时候，用户依然可以在页面上自由滚动、点击，页面不会卡死（这就是“异步”的魅力）。**
	
	3. **服务器处理：** 服务器接收到请求，处理逻辑，并准备好数据。
	
	4. **接收响应 (Response)：** 服务器将结果（通常是一串 JSON 数据和 HTTP 状态码，如 200 表示成功）发送回浏览器。
	
	5. **更新页面：** JavaScript 接收到返回的数据，通过操作 DOM（文档对象模型），将新数据动态渲染到页面的特定位置，整个过程用户甚至感觉不到页面的跳转。
