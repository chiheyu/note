如果我是你，我不会逐行纯手写全部基础代码，也不会让代码生成器一键生成完整后端后直接开写业务。

我会采用更稳的方案：

> 代码生成器生成基础骨架 + 人工重构业务边界 + Codex Agent 辅助补业务代码。

这是当前项目最合适的路线。

## 我的明确建议

你的 10 张表已经建好，实体类、Mapper、基础 Service、基础 XML 这类代码高度重复。纯手写会浪费时间，而且容易出现字段名、类型、注解、包路径不一致的问题。

MyBatis-Plus 官方的新版代码生成器 `FastAutoGenerator` 本身就是为这种场景准备的，可以按数据库表快速生成 `entity`、`mapper`、`service`、`service.impl`、`mapper.xml` 等包结构。官方示例里也正是通过 `packageConfig` 指定这些目录，并通过 `FastAutoGenerator.create(...).execute()` 执行生成。

但是，代码生成器只能解决“重复模板代码”，不能解决你的业务复杂度。MyBatis Generator 官方文档也明确说明，它能根据表生成访问数据库的基础代码，减少 CRUD 初始化工作，但 join 查询、存储过程或复杂 SQL 仍然需要手写。

所以我的方案是：

* 生成器负责 **60%** 的基础代码
* 你和 Codex Agent 负责 **40%** 的业务代码

## 一、哪些代码应该生成？

这些应该用代码生成器：

| 模块 | 是否生成 | 原因 |
| :--- | :--- | :--- |
| Entity 实体类 | 生成 | 字段多，重复性高 |
| Mapper 接口 | 生成 | 基础结构固定 |
| Mapper.xml | 生成基础版 | 后续手动补复杂 SQL |
| Service 接口 | 生成基础版 | 可以先继承 IService |
| ServiceImpl | 生成基础版 | 可以先继承 ServiceImpl |
| 基础 Controller | 可生成，但不建议直接用 | 容易生成通用 CRUD，和你的权限设计冲突 |

尤其是这几类表，生成器非常适合：

* `sys_user`
* `sys_level_rule`
* `lab_info`
* `lab_device`
* `lab_material`
* `lab_announcement`
* `sys_operation_log`

它们大部分都有标准的增删改查需求。

## 二、哪些代码必须手写？

这些不能交给代码生成器直接完成：

| 模块 | 必须手写原因 |
| :--- | :--- |
| 登录认证 | 涉及 JWT / Session / 密码加密 / 权限上下文 |
| 权限注解 | 要和 API 权限清单严格对应 |
| 设备预约提交 | 有时间冲突、设备锁、教师审批规则 |
| 设备预约审批 | 有状态机，不允许通用 updateStatus |
| 耗材申请提交 | 有额度计算、危险等级判断、快照字段 |
| 耗材最终确认 | 有事务、库存原子扣减、库存流水 |
| Dashboard 查询 | 聚合统计，不是普通 CRUD |
| 操作日志切面 | 需要 AOP 或拦截器处理 |
| 数据范围控制 | 学生 Own、教师 Assigned、管理员全量 |
| DTO / VO | 面向接口，不应直接暴露 Entity |

你这个系统最核心的后端价值不在 CRUD，而在：

**权限控制 + 状态机 + 事务一致性 + 业务校验**

这些必须认真手写。

## 三、我会采用的实际开发流程

我建议你不要完全按：

`实体类 -> Mapper -> XML -> Service -> Controller`

这种线性方式走。

更好的顺序是：

1. 项目基础骨架
2. 代码生成器生成 Entity / Mapper / XML / Service 基础代码
3. 建立通用基础设施
4. 按模块手写业务 Service
5. 按 API 权限清单手写 Controller
6. 写接口测试

具体如下。

先不要急着生成代码，先搭好这些基础包：

```text
│   └── utils

```

先写好这些通用类：
 * Result<T>
 * PageResult<T>
 * BusinessException

 * UserContext
 * PermissionConstants
枚举类也先写：
 * UserRoleEnum

 * StockChangeTypeEnum
 * AnnouncementStatusEnum

这些东西不能靠生成器生成，因为它们决定整个项目的编码风格。

### 第 2 步：用代码生成器生成基础代码
我推荐使用 MyBatis-Plus FastAutoGenerator。
生成范围：
 * Entity
 * Mapper
 * Mapper.xml
 * Service
 * ServiceImpl
不建议一开始生成 Controller，原因是生成器生成的 Controller 往往是普通 CRUD 风格，而你的系统已经明确要求：
 * 禁止通用 updateStatus
 * 审批必须使用业务动作接口
 * 系统管理员不得调用业务审批接口
 * 实验室管理员不得查看操作日志
如果生成通用 Controller，后面反而要删很多代码。

### 第 3 步：生成代码不要直接覆盖主目录
我会让生成器先输出到临时目录：
$/generated-code$
不要直接输出到：
$/src/main/java$
原因是：
 1. 方便人工检查。
 2. 避免覆盖你已经写好的业务代码。
 3. 可以按模块逐步迁移。
 4. 后续表结构改动时，可以重新生成对比差异。
推荐流程：
```text
生成到 generated-code
↓
检查 Entity 字段类型
↓
检查 Mapper 包名
↓
检查 XML namespace
↓
检查 Lombok / TableName / TableId 注解
↓
复制到正式 src/main/java
```

## 四、你的项目里生成器需要特别注意的点
### 1. $TINYINT$ 不要被错误生成成 $Boolean$
你的表里大量使用 $TINYINT$：
 * role
 * level
 * status
 * device_level
 * dangerous_level
 * apply_type
 * change_type
 * deleted
这些都应该生成成：
```java
private Integer status;
```

或者：
```java
private Byte status;
```

我建议统一用：
$Integer$
因为后端枚举转换、$JSON$ 返回、条件判断更方便。
$MyBatis-Plus$ 文档也提到 $MySQL tinyint$ 字段类型转换可能需要特别处理，必要时可以通过类型转换配置把$TINYINT$ 转成 $Integer$。

### 2. 时间类型统一
建议生成结果里统一使用：
 * LocalDateTime
 * LocalTime
对应关系：

| MySQL 类型 | Java 类型 |
|---|---|
| DATETIME | LocalDateTime |
| TIME | LocalTime |
| DATE | LocalDate |
不要用老的：
$Date$

### 3. $DECIMAL$ 用 $BigDecimal$
这些字段必须是：
$BigDecimal$
例如：
 * max_material_percentage
 * percentage_at_apply
不要用 $Double$，否则比例计算可能有精度问题。
### 4. 逻辑删除字段加注解
有 $deleted$ 字段的实体建议加：
```java
@TableLogic
private Integer deleted;
```

适用表：
 * sys_level_rule
 * sys_user
 * lab_device
 * lab_material
 * lab_announcement
不适用：
 * device_reservation
 * material_apply
 * material_stock_record
 * sys_operation_log
因为这些是业务历史和审计凭证，不应该逻辑删除。

### 5. 自动填充字段要统一处理
这些字段建议用 $MyBatis-Plus$ 自动填充：
 * create_time
 * update_time
 * create_by
 * update_by
实体中：
```java
@TableField(fill = FieldFill.INSERT)
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE)
private LocalDateTime updateTime;
```

$createBy、updateBy$ 可以通过当前登录用户上下文填充。

## 五、$Mapper.xml$ 怎么处理？
我建议：
**基础 $CRUD$ 不写 $XML$**
$MyBatis-Plus$ 的 $BaseMapper$ 已经够用。
例如：
```java
public interface LabDeviceMapper extends BaseMapper<LabDevice> {
}
```

这种查询不需要 $XML$：
 * 根据 $id$ 查
 * 分页查
 * 条件查
 * 新增
 * 更新
 * 逻辑删除
**复杂查询再写 $XML$**
这些必须写 $XML$ 或自定义 $Mapper$ 方法：
**设备预约**
 * 查询预约冲突
 * 查询教师待审批预约
 * 查询管理员待审批预约
 * 查询设备使用率排行
**耗材申请**
 * 查询教师待审批特殊耗材申请
 * 查询管理员待确认申请
**库存流水**
 * 耗材消耗排行
 * 按时间范围查询库存流水
**$Dashboard$**
 * 今日预约数量
 * 待审批预约数量
 * 待审批耗材申请数量
 * 库存预警数量
 * 设备使用率排行
 * 耗材消耗排行
所以 $Mapper.xml$ 不要盲目写满，应该是：
 * 基础 $CRUD$：$MyBatis-Plus$
 * 复杂查询：$Mapper.xml$
## 六、$Service$ 层必须手写
$Service$ 层是你这个项目的核心。
不要只写这种：
```java
public interface DeviceReservationService extends IService<DeviceReservation> {
}
```

你应该定义业务动作方法。
例如设备预约：
```java
public interface DeviceReservationService {

    Long createReservation(CreateReservationRequest request);

    void teacherApprove(Long reservationId, ApproveRequest request);

    void teacherReject(Long reservationId, RejectRequest request);

    void adminApprove(Long reservationId, ApproveRequest request);

    void adminReject(Long reservationId, RejectRequest request);

    void cancelOwn(Long reservationId);

    void finish(Long reservationId);
}
```

耗材申请：
```java
public interface MaterialApplyService {

    Long createApply(CreateMaterialApplyRequest request);

    void teacherApprove(Long applyId, ApproveRequest request);

    void teacherReject(Long applyId, RejectRequest request);

    void adminApprove(Long applyId, ApproveRequest request);

    void adminReject(Long applyId, RejectRequest request);

    void cancelOwn(Long applyId);

    void finish(Long applyId);
}
```

这样才能保证状态机清晰。
千万不要设计：
```java
void updateStatus(Long id, Integer status);
```

这个接口会破坏权限矩阵。
## 七、$Controller$ 也建议手写
$Controller$ 必须严格对应 $API$ 权限清单。
例如：
```java
@PostMapping("/reservations")
@RequirePermission("reservation:create")
public Result<Long> createReservation(@RequestBody CreateReservationRequest request) {
    return Result.success(reservationService.createReservation(request));
}
```

不要让生成器生成这种接口：
```java
@PutMapping("/{id}")
public Result<?> update(@PathVariable Long id, @RequestBody DeviceReservation entity)
```

这种接口风险很大，因为前端可能直接传：
```json
{
  "status": 3
}
```

然后绕过审批流程。

## 八、我会如何使用 $Codex Agent$
我不会让 $Codex Agent$ 一次性生成整个后端。
我会这样用：

### 第一轮：让它生成基础工程结构
给 $Codex Agent$ 的任务：
> 基于 $Spring Boot + MyBatis-Plus$ 创建项目基础结构：
>  1. common/result
>  2. common/exception
>  3. common/enums
>  4. config
>  5. security
>  6. module 分包
>    不要生成业务逻辑。

### 第二轮：让它根据 $schema.sql$ 生成 Entity
任务：
> 根据 schema.sql 生成 Entity 类。
> 要求：
>  1. BIGINT -> Long
>  2. DATETIME -> LocalDateTime
>  3. TIME -> LocalTime
>  4. DECIMAL -> BigDecimal
>  5. TINYINT -> Integer
>  6. 使用 Lombok
>  7. 使用 @TableName
>  8. 主键使用 @TableId(type = IdType.AUTO)
>  9. deleted 字段使用 @TableLogic
>  10. createTime/updateTime 使用自动填充

### 第三轮：生成 $Mapper$ 和基础 $Service$
任务：
> 为所有实体生成 Mapper、Service、ServiceImpl。
> Mapper 继承 BaseMapper。
> Service 继承 IService。
> ServiceImpl 继承 ServiceImpl。
> 暂不生成 Controller。

### 第四轮：手写核心业务模块
按模块让 $Codex Agent$ 分批写：
 * 设备预约模块
 * 耗材申请模块
 * 库存模块
 * 权限模块
 * 公告模块
 * 用户模块
 * $Dashboard$ 模块
每次只让它做一个模块，不要一次性生成全部。
