## 一、进程与线程（“动态执行的实体”）

### 1. 进程的基本概念与特征
* **程序与进程的本质区别：** 程序是存放在磁盘上的静态指令集合；进程是程序的一次动态执行过程。
* **进程的五大特征：**
  * **动态性（最基本特征）：** 进程有创建、活动、暂停、终止等过程。
  * **并发性：** 多个进程实体同存于内存中，能在一段时间内同时运行。
  * **独立性：** 进程是系统**进行资源分配和调度的独立单位**。
  * **异步性：** 进程以不可预知的速度向前推进（需要同步机制解决）。
  * **结构性：** 进程由程序段、数据段和 PCB（进程控制块）三部分组成。

### 2. 进程的内存映像与 PCB
当一个程序装入内存运行时，构成了进程的物理实体：
* **程序段：** 存放要执行的机器指令（通常是只读的，可被多个进程共享）。
* **数据段：** 存放程序运行时的全局变量、静态变量。
* **堆 (Heap)：** 动态分配的内存区（如 C 语言的 `malloc`）。
* **栈 (Stack)：** 存放局部变量、函数调用的参数、返回地址（由编译器自动分配释放）。
* **PCB (Process Control Block, 进程控制块)：** **进程存在的唯一标志**。包含进程描述信息（PID、UID）、进程控制和管理信息（CPU、磁盘、网络利用情况）、资源分配清单（代码段、数据段指针、打开的文件描述符表）和 CPU 相关信息（各种寄存器值，用于上下文切换）。
![](assets/第二章%20进程管理/file-20260904.jpg)
### 3. 进程状态与转换（五态模型与挂起机制）
408 重点考察五态模型及挂起状态的理解：
* **五态模型：**
  * **创建态 (New)：** 正在分配资源、初始化 PCB。
  * **就绪态 (Ready)：** 万事俱备，只欠 CPU。在就绪队列中等待调度。
  * **运行态 (Running)：** 占有 CPU，正在执行指令。
  * **阻塞态 (Blocked/Waiting)：** 正在等待某一事件（如 I/O 操作、请求缓冲区资源）发生而暂停运行。**（注意：进程主动请求阻塞）**
  * **终止态 (Terminated)：** 进程正常结束或异常被撤销，系统正在回收资源。
* **状态转换核心考点：**
  * 运行 $\to$ 阻塞：**主动行为**（如调用 `read()` 等待外设）。
  * 阻塞 $\to$ 就绪：**被动行为**（如外设中断通知 I/O 完成），**绝对不能直接转为运行态**。
  * 运行 $\to$ 就绪：时间片用完或被更高优先级进程**抢占**。
* **挂起状态 (Suspend)：** 为了缓解内存压力，操作系统将某些阻塞或就绪的进程**换出到外存（磁盘）**，形成“挂起阻塞态”和“挂起就绪态”。被挂起的进程不占用内存空间。

### 4. 线程 (Thread) 机制及其多线程模型
引入进程是为了“并发”，引入线程是为了“进一步提高并发度、降低系统开销”。
* **线程的本质：** 线程是 **CPU 调度的基本单位**。同一进程内的多个线程共享该进程的地址空间、文件资源等。
* **进程与线程的对比核心：**
  * **资源分配：** 进程是资源分配的基本单位；线程不拥有系统资源（除了一点必不可少的 TCB、寄存器和栈），但可以共享所属进程的资源。
  * **切换开销：** 进程切换需要切换虚拟地址空间（涉及刷新 TLB / 快表），开销巨大；同进程下的线程切换不涉及虚拟地址空间的切换，开销极小。
* **多线程模型：**
  * **用户级线程 (ULT)：** 线程管理全靠用户态的“线程库”。内核看不见它，**调度仍以进程为单位**。优点是切换快，缺点是**一个线程阻塞，整个进程全部阻塞；无法发挥多处理器的并行优势**。
  * **内核级线程 (KLT)：** 线程管理由 OS 内核完成。**调度以线程为单位**。优点是并发能力强，阻塞处理更灵活，缺点是频繁的用户态/内核态切换开销大。
  * **多对一、一对一、多对多模型：** 描述用户级线程如何映射到内核级线程。

## 二、进程间通信 (IPC)

各进程的内存地址空间是相互独立的，进程间通信必须依赖操作系统的支持。

### 1. 共享内存 (Shared Memory)
* 操作系统在内存中开辟一块共享空间，多个进程将其映射到自己的虚拟地址空间中。
* **特点：** 最快的数据交换方式，无需数据拷贝。
* **注意：** 操作系统只负责分配空间，**读写的同步与互斥（如 P/V 操作）必须由用户进程自己负责**。

### 2. 消息传递 (Message Passing)
进程间的数据交换以**格式化的消息 (Message)** 为单位。
* **直接通信：** 发送方直接指定接收方的进程 ID，OS 将消息直接挂到接收方 PCB 的消息队列中。
* **间接通信（信箱通信）：** 通过 OS 维护的中间实体（信箱）进行收发。

### 3. 管道通信 (Pipe)
* **本质：** 内存中开辟的一个大小固定的**环形缓冲区**（通常是 1 个内存页，如 4KB）。
* **特征（高频考点）：**
  * 管道是**半双工通信**（同一时刻只能单向传输）。如果要实现全双工，必须申请**两个**管道。
  * 各进程必须**互斥**访问管道。
  * 管道写满时，写进程阻塞；管道读空时，读进程阻塞。
  * 数据以字符流的形式写入，一旦读出就被抛弃（不能复读）。
  * 传统匿名管道只能用于有**亲缘关系**（如父子进程）的进程间；命名管道（FIFO）可用于任意进程。

## 三、CPU 调度（必考计算题核心）

### 1. 调度的三个层次
* **高级调度（作业调度）：** 从外存后备队列中挑选作业，分配内存并建立 PCB（新建态 $\to$ 就绪态）。频率最低。
* **中级调度（内存调度）：** 决定将哪些进程挂起调出至外存，或将哪些挂起进程重新调入内存。频率中等。
* **低级调度（进程调度）：** 从就绪队列中选取进程分配 CPU（就绪态 $\to$ 运行态）。**频率最高**（如几十毫秒一次），是 OS 最核心的部分。
![](assets/第二章%20进程管理/file-20260904%202.jpg)
### 2. 进程调度的时机与方式
* **不能进行进程切换的情况：**
  * 处理中断的过程中。
  * 进程在**操作系统内核程序临界区**中（注意：普通临界区是可以调度的！只有内核数据结构相关的临界区如就绪队列加锁时不能调度）。
  * 其他需要完全屏蔽中断的原子操作过程中。
* **调度方式：** 非抢占式（主动让出 CPU） vs 抢占式（强行剥夺 CPU，适用于分时和实时系统）。

### 3. 调度算法性能评价指标（核心公式）
* **周转时间：** 作业从提交到完成所经历的时间。
  $$周转时间 = 完成时间 - 提交到达时间$$
* **带权周转时间：** 衡量作业等待时间的相对大小，必然 $\ge 1$。
  $$带权周转时间 = \frac{周转时间}{实际运行时间}$$
* **等待时间：** 进程处于等处理机状态的时间之和。对于作业，等待时间 = 周转时间 - 运行时间 - I/O时间。
* **响应时间：** 从用户提交请求到系统**首次**产生响应的时间。

### 4. 典型调度算法拆解
| 算法名称              | 原则                                  | 特点与适用场景                                          | 是否抢占         | 优缺点                                      |
| :----------------: | :----------------------------------: | :-----------------------------------------------: | :-----------: | :---------------------------------------: |
| **FCFS (先来先服务)**  | 按照到达队列的先后顺序                         | 适合批处理系统                                          | 非抢占          | 对长作业有利，**对短作业极其不利**，易产生饥饿（Convoy Effect） |
| **SJF (短作业优先)**   | 估计运行时间最短的优先                         | 平均等待/周转时间最短                                      | 非抢占/抢占(SRTN) | 对短作业有利，**长作业极易饥饿**                       |
| **HRRN (高响应比优先)** | 每次调度计算响应比最高者                        | $响应比 = \frac{等待+要求服务}{要求服务} = 1 + \frac{等待}{服务}$ | 非抢占          | 兼顾长短作业，等待越久优先级越高，**不饥饿**，但计算开销大          |
| **RR (时间片轮转)**    | 按时间片分配，用完排到队尾                       | 适合分时交互系统                                         | 抢占式          | 响应快；若时间片太大退化为 FCFS，太小则切换开销极大             |
| **多级反馈队列**        | **408最爱**。设置多个优先级队列，优先级逐级降低，时间片逐级变大 | 综合了以上所有优点，是大多数商用 OS 的默认算法                        | 抢占式          | 对短进程、I/O进程友好，若长作业不断被抢占也可能饿死              |
### 5. 多处理机调度

#### (1) 多处理机系统架构分类
| 架构类型              | 结构特点                 | 调度权分配                                            | 优缺点 / 408考点                        |
| :----------------: | :-------------------: | :-----------------------------------------------: | :---------------------------------: |
| **非对称多处理机 (AMP)** | 主从式架构 (Master-Slave) | 仅**主 CPU** 运行内核并负责调度管理；**从 CPU** 仅执行由主 CPU 分配的任务 | 结构简单、无并发调度冲突；但**主 CPU 易成为系统性能瓶颈**  |
| **对称多处理机 (SMP)**  | 对等架构 (Peer-to-Peer)  | **所有 CPU 地位对等**，均可独立运行内核并参与进程调度                  | 现代多核主流架构；资源利用率高，但**需解决内核并发与数据锁竞争** |

#### (2) SMP 的核心矛盾：亲和性 vs 负载平衡
- **处理器亲和性 (Processor Affinity)**：进程在某个 CPU 上运行后，其私有数据已加载到该 CPU 的局部 Cache 中。若跨 CPU 迁移，原 Cache 必须置为无效并重新填充，开销巨大。因此调度策略**应尽量让进程运行在同一 CPU 上**。
  - **软亲和 (Soft Affinity)**：调度程序*尽量*保持在原 CPU，但允许在负载失衡严重时进行跨核迁移。
  - **硬亲和 (Hard Affinity)**：进程通过系统调用（如 Linux 下的 `sched_setaffinity`）**显式绑定到固定 CPU**，系统绝不允许其跨核迁移。
- **负载平衡 (Load Balancing)**：设法将任务均匀分配到所有 CPU，避免“一核有难、多核围观”（部分 CPU 过载排队，而其他 CPU 处于空闲状态）。
- **矛盾与权衡**：负载平衡所依赖的“任务迁移”必然破坏 Cache 亲和性。因此实际系统中通常设定阈值，**仅当负载不平衡达到一定程度后，才会触发进程迁移**。

#### (3) 两种多处理机调度方案对比
| 调度方案 | 就绪队列设计 | 处理器亲和性 | 负载平衡能力 | 优缺点与考点 |
| :---: | :---: | :---: | :---: | :---: |
| **公共就绪队列** | 所有 CPU 共享**单个全局队列** | **差**（进程易在不同 CPU 间反复跳跃，Cache 命中率低） | **极佳**（CPU 空闲即取任务，天然实现负载均衡） | 全局队列需互斥访问，**高并发下锁竞争严重**，成为系统扩展瓶颈 |
| **私有就绪队列** | 每个 CPU 拥有**独立的本地就绪队列** | **极佳**（进程通常固定在本地 CPU 执行，亲和性高） | **差**（易出现负载倾斜，必须依赖外部迁移机制） | 极大减少了全局锁竞争；是**现代操作系统的绝对主流方案** |

#### (4) 负载平衡的实现方式（针对私有就绪队列）
- **推迁移 (Push Migration)**：由特定系统内核程序**周期性巡检**各 CPU 负载，一旦发现失衡，便将超载 CPU 队列中的任务“推”到空闲 CPU 队列中。
- **拉迁移 (Pull Migration)**：当某个 CPU **变为空闲**时，主动探测其他超载 CPU，并从其就绪队列中“拉取（窃取）”任务到本地执行。
- **实战考点**：在现代实际操作系统中，推迁移与拉迁移通常**结合使用**以保证系统的响应与高吞吐。

## 四、进程同步与互斥（大题重灾区）

### 1. 临界资源与互斥访问原则
* **临界资源：** 一段时间内**只允许一个进程使用**的资源（如打印机、共享变量）。
* **同步（直接制约）：** 进程间为协作完成任务，必须有执行的先后顺序（如 A 算完 B 才能用）。
* **互斥（间接制约）：** 多个进程竞争同一临界资源。
* **实现互斥的四个软硬件原则（必须背诵）：**
  1. **空闲让进：** 临界区空闲时，允许一个请求进入的进程进入。
  2. **忙则等待：** 临界区已被占用，其他试图进入的进程必须等待。
  3. **有限等待：** 对请求进入的进程，应保证在有限时间内进入（防死锁）。
  4. **让权等待：** 进程不能进入临界区时，应立即释放处理机（防忙等，仅记录型信号量和管程做到了）。

### 2. 实现互斥的软件算法（核心思想推演）
* **单标志法：** 两个进程轮换使用。**缺点：** 违背“空闲让进”（如果轮到 A，但 A 不想进，B 就永远进不去）。
* **双标志先检查：** 先看对方标志，再设自己标志。**缺点：** 违背“忙则等待”（并发执行时可能同时进入）。
* **双标志后检查：** 先设自己标志，再看对方标志。**缺点：** 违背“空闲让进”和“有限等待”（可能产生双方都等对方，导致**死锁/饥饿**）。
* **Peterson 算法：** 结合双标志与单标志（谦让原则）。
  ```c
  // 进程 P0
  flag[0] = true;     // 表达意愿
  turn = 1;           // 谦让给对方，进程(P1)，1指P1
  while (flag[1] && turn == 1); // 对方有意愿且是我谦让的，我等
  // 进入临界区...
  flag[0] = false;    // 退出
  ```
### 3. 信号量机制 (Semaphore)

信号量本质是一个变量，只能被两个标准原语 `wait(S)` 和 `signal(S)`（即 P、V 操作）访问。

- **整型信号量：** 仅仅是一个整数，`wait` 中使用 `while (S<=0);` 会导致**忙等**（未实现让权等待）。
    
- **记录型信号量（现代 OS 基础）：** 引入了阻塞队列 `block()` 和唤醒 `wakeup()`，完美解决“让权等待”。
	```C
	typedef struct {
		int value,
		struct process *list;
	} semaphore;
	// P操作：申请资源
    wait(semaphore *S) {
        S->value--;
        if (S->value < 0) {
            add this process to S->list;
            block(); // 阻塞自己
        }
    }
    // V操作：释放资源
    signal(semaphore *S) {
        S->value++;
        if (S->value <= 0) { // 注意是 <= 0，说明原本有人在等
            remove a process P from S->list;
            wakeup(P); // 唤醒等待者
        }
    }
    ```


#### **（1）实现互斥**
* 进入区申请资源，退出区释放资源。为临界资源设置互斥信号量 `mutex`，**初值通常设为 1**。P、V 操作必须**紧密夹紧临界区且成对出现**在同一进程中。
```c
semaphore mutex = 1; // 初始化互斥信号量为 1

void P1() {
    while (1) {
        wait(mutex);   // 进入区：P 操作加锁，申请访问
        // 临界区代码（访问共享临界资源）
        signal(mutex); // 退出区：V 操作解锁，唤醒等待进程
        // 剩余区代码
    }
}
```

 #### **（2）实现同步**
* 协调并发进程按特定先后顺序执行。设置同步信号量 S，初值设为 0（代表后操作期望的条件暂未达成）。核心口诀：“前 V 后 P”（先执行的操作完成后执行 signal，后执行的操作执行前执行 wait）。
```C
semaphore S = 0; // 初始化同步信号量为 0

void P1() {
    // 运行前操作 code1
    signal(S); // V 操作：通知系统“前操作已完成”
}

void P2() {
    wait(S);   // P 操作：检查“前操作是否完成”，未完成则阻塞自己
    // 运行后操作 code2
}
```

 #### **（3）实现前驱关系**
* 本质是多对同步关系的组合（前驱图 DAG）。为前驱图中的每一条有向边设置一个初值为 0 的信号量；弧尾进程（前驱）完成后执行 signal，弧头进程（后继）执行前执行 wait。
```C
// 示例：S1 -> S2, S1 -> S3, S2 -> S4, S3 -> S4
semaphore a = 0; // 对应边 S1 -> S2
semaphore b = 0; // 对应边 S1 -> S3
semaphore c = 0; // 对应边 S2 -> S4
semaphore d = 0; // 对应边 S3 -> S4

void P1() {
    // 执行 S1 代码
    signal(a); // 激活 S2
    signal(b); // 激活 S3
}

void P2() {
    wait(a);   // 等待 S1
    // 执行 S2 代码
    signal(c); // 激活 S4
}

void P3() {
    wait(b);   // 等待 S1
    // 执行 S3 代码
    signal(d); // 激活 S4
}

void P4() {
    wait(c);   // 等待 S2
    wait(d);   // 等待 S3
    // 执行 S4 代码
}
```

### 4. 管程 (Monitor)

信号量写起来容易出错（PV 顺序写错直接死锁）。**管程**是编程语言提供的一种高级同步机制（如 Java 的 `synchronized`）。
- **特征：** 管程封装了共享数据和对数据的操作；**每次仅允许一个进程进入管程**（由编译器自动实现互斥）；引入了条件变量（Condition Variable）如 `x.wait` 和 `x.signal` 解决同步阻塞问题。

## 五、经典同步问题模型（解题模板）

### 1. 生产者-消费者问题

- **模型：** 一群生产者向共享缓冲区（容量 N）放数据，消费者取数据。
- **信号量设置：** `mutex = 1`（互斥），`empty = N`（同步，初始为空），`full = 0`（同步，初始满为0）。
- **大坑防范：** **实现互斥的 P 操作一定要在实现同步的 P 操作之后！**（先 P(empty)，再 P(mutex)），否则会导致死锁（先 P(mutex)，缓冲区已满，再 P(emtey)，陷入死锁）。V 操作的顺序无所谓。
```c
semaphore mutex = 1; // 互斥信号量：互斥访问共享缓冲区
semaphore empty = N; // 同步信号量：空闲缓冲区数量（初值为 N）
semaphore full = 0;  // 同步信号量：已占用的缓冲区数量（初值为 0）

void producer() {
    while (1) {
        // 生产一个数据 item
        wait(empty); // 1. 申请空缓冲区（同步 P）
        wait(mutex); // 2. 申请进入临界区（互斥 P，必须在 wait(empty) 之后！）

        // 将 item 放入缓冲区（临界区操作）

        signal(mutex); // 3. 退出临界区
        signal(full);  // 4. 释放满缓冲区资源，唤醒消费者（同步 V）
    }
}

void consumer() {
    while (1) {
        wait(full);  // 1. 申请满缓冲区（同步 P）
        wait(mutex); // 2. 申请进入临界区（互斥 P）

        // 从缓冲区取走 item（临界区操作）

        signal(mutex); // 3. 退出临界区
        signal(empty); // 4. 释放空缓冲区资源，唤醒生产者（同步 V）
        // 消费数据 item
    }
}
```

### 2. 读者-写者问题

- **规则：** 读读允许并存；读写互斥；写写互斥。
- **核心技巧（读者优先）：** 引入整型变量 `count` 记录读者数量。只有第一个读者负责加锁 `P(rw)`，最后一个读者负责解锁 `V(rw)`。对 `count` 的修改必须用互斥信号量 `mutex` 保护。
```c
int count = 0;       // 记录当前正在读取的读者数量
semaphore mutex = 1; // 互斥信号量：保护对全局变量 count 的互斥修改
semaphore rw = 1;    // 互斥信号量：用于实现读/写互斥、写/写互斥

void reader() {
    while (1) {
        wait(mutex);     // 保护 count
        if (count == 0) {
            wait(rw);    // 第 1 个读者负责“加锁”（阻断写者）
        }
        count++;
        signal(mutex);

        // 读文件（临界区操作，允许多个读者同时执行）

        wait(mutex);     // 保护 count
        count--;
        if (count == 0) {
            signal(rw);  // 最后一个离开的读者负责“解锁”（唤醒写者）
        }
        signal(mutex);
    }
}

void writer() {
    while (1) {
        wait(rw);        // 申请写文件互斥权
        // 写文件（临界区操作，独占）
        signal(rw);      // 释放写文件互斥权
    }
}
```

```c
//读写公平法
int count = 0;
semaphore mutex = 1; // 保护 count
semaphore rw = 1;    // 读写互斥锁
semaphore w = 1;     // 排队锁：用于实现“读写公平”，阻止后续读者插队

void reader() {
    while (1) {
        wait(w);         // 读者先领排队号（若已有写者在等，新读者在此被阻塞）
        wait(mutex);
        if (count == 0) {
            wait(rw);    // 第一个读者锁住文件
        }
        count++;
        signal(mutex);
        signal(w);       // 释放排队锁，允许下一进程排队

        // 读文件 reading...

        wait(mutex);
        count--;
        if (count == 0) {
            signal(rw);  // 最后一个读者释放文件
        }
        signal(mutex);
    }
}

void writer() {
    while (1) {
        wait(w);         // 写者领排队号，阻断后续新读者的排队
        wait(rw);        // 申请独占写
        // 写文件 writing...
        signal(rw);
        signal(w);       // 释放排队锁
    }
}
```
### 3. 哲学家进餐问题

- **痛点：** 5 个人竞争 5 根筷子，如果每个人都先拿左边再拿右边，会集体死锁。
- **解决方案：**
	1. 限制最多 4 人同时进餐。
    2. 奇数号先拿左边，偶数号先拿右边。
    3. 用 AND 型信号量或管程，要求同时拿起左右两根筷子。
```c
// 方案 1：限制最多 4 人同时进餐
semaphore chopstick[5] = {1, 1, 1, 1, 1}; // 5 根筷子的互斥信号量
semaphore count = 4;                      // 至多允许 4 位哲学家同时拿筷子

void philosopher(int i) {
    while (1) {
        // 思考 thinking...
        wait(count);                    // 申请进餐名额
        wait(chopstick[i]);             // 拿左边的筷子
        wait(chopstick[(i + 1) % 5]);   // 拿右边的筷子

        // 进餐 eating...

        signal(chopstick[(i + 1) % 5]); // 放下右边的筷子
        signal(chopstick[i]);           // 放下左边的筷子
        signal(count);                  // 归还进餐名额
    }
}
```
```c
// 方案 2：奇偶号拿筷子顺序不同（破坏环路等待）
semaphore chopstick[5] = {1, 1, 1, 1, 1};

void philosopher(int i) {
    while (1) {
        // 思考 thinking...
        if (i % 2 == 1) { // 奇数号哲学家：先拿左，再拿右
            wait(chopstick[i]);
            wait(chopstick[(i + 1) % 5]);
        } else {          // 偶数号哲学家：先拿右，再拿左
            wait(chopstick[(i + 1) % 5]);
            wait(chopstick[i]);
        }

        // 进餐 eating...

        signal(chopstick[i]);
        signal(chopstick[(i + 1) % 5]);
    }
}
```

## 六、死锁 (Deadlock)

### 1. 概念辨析

- **死锁：** 多个进程互相等待对方手中的资源，无外力介入永远僵持。
- **饥饿：** 某进程长期得不到 CPU 或资源（如长作业在 SJF 中饿死）。
- **死循环：** 代码逻辑错误，占用 CPU 空转（前两者是 OS 资源分配问题）。

### 2. 死锁的四个必要条件（缺一不可）

1. **互斥条件：** 抢夺的是非共享资源。
2. **不剥夺条件：** 进程获得资源在未使用完前，不能强行抢占。
3. **请求并保持条件：** 进程持有一个资源，又去请求新资源被阻塞，且不释放现有资源。
4. **循环等待条件：** 存在进程资源的闭合环路。（**注意：有环路不一定死锁，死锁一定有环路**）。

### 3. 死锁的处理策略

|  **策略**  | **实施阶段** | **核心方法**                                                    |
| :------: | :------: | ----------------------------------------------------------- |
| **预防死锁** |  事前静态干预  | 破坏四个必要条件之一。例如：资源按序号有序分配（破坏环路等待）；一次性申请所有资源（破坏请求并保持）。资源利用率极低。 |
| **避免死锁** | 运行时动态干预  | **银行家算法**。在每次分配前，模拟分配并检查系统是否进入**不安全状态**。寻找是否存在一个“安全序列”。     |
| **死锁检测** |   事后发现   | 构建资源分配图，寻找循环等待。如果图**可完全化简**，则无死锁（死锁定理）。                     |
| **死锁解除** |   事后恢复   | 1. 资源剥夺法；2. 撤销进程法（按代价大小）；3. 进程回退法。                          |

### 4. 银行家算法计算逻辑（必考）

- **核心数据结构：** `Max` (最大需求矩阵)，`Allocation` (已分配矩阵)，`Need` (尚需矩阵 = Max - Allocation)，`Available` (可用资源向量)。
- **安全性算法：** 寻找一个使得 `Need[i] <= Available` 的进程，假设让它运行完，回收它的 `Allocation` 到 `Available` 中，反复进行。若所有进程都能执行完，这就是一个**安全序列**

## 七、高频易错点防坑指南

1. **陷阱：进程阻塞是因为调度算法决定的吗？**
    - **错！** 阻塞是进程**主动调用**（如等待 I/O、申请 PV 失败）引起的，属于进程自身行为。调度算法只管让谁进入运行态，不管让谁进入阻塞态。
    
2. **判断：P 操作一定会导致阻塞吗？**
    - **错！** P 操作执行 `S.value--`，只有当 `S.value < 0` 时才会阻塞。如果资源足够，不会阻塞。同理，V 操作也不一定会唤醒进程。
    
3. **辨析：管程中的 `wait` 和 信号量的 `P` (wait) 是一回事吗？**
    - **错！** 管程的条件变量 `x.wait` 执行时，**一定会挂起本进程，并释放管程的互斥权**。而信号量的 P 操作只有资源不够才阻塞。
    
4. **陷阱：系统处于不安全状态一定会发生死锁吗？**
    - **错！** 不安全状态仅仅是**可能**发生死锁。但处于安全状态**一定不会**发生死锁。死锁状态必定是不安全状态的子集。
    
5. **易错：多级反馈队列中，长作业被降级，它的时间片变大还是变小？**
    - **变大！** 优先级越低的队列，分配到的时间片反而越长，这是为了补偿它漫长的等待时间，减少上下文切换开销。

## 八、第二章核心结论清单总结

- **三级调度映射：** 高级调度=外存$\to$内存；中级调度=外存$\leftrightarrow$内存(挂起)；低级调度=就绪$\to$运行。
- **进程实体：** PCB 是进程存在的唯一标志。线程共享代码和数据，但不共享栈和寄存器。
- **同步互斥核心：** 互斥保证“不能同时进入”，同步保证“A做完B再做”。PV 操作中，同步 P 必定在互斥 P 外层。
- **死锁的底线：** 预防靠打破条件，避免靠银行家，检测靠化简图。
- **死锁产生的极值计算：** 假设系统有 m 个同类资源被 n 个进程共享，每个进程最多需要 k 个资源，则发生死锁的极端情况是每个进程都占有 $k-1$ 个资源且系统不剩资源，即 $n(k-1) = m$。故不发生死锁的条件为 $n(k-1) + 1 \le m$。
