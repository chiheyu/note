## 一、传输层解决什么问题与核心功能

#### 1. 传输层的核心功能
网络层（IP协议）为主机之间提供逻辑通信，而传输层为**应用进程之间**提供端到端的逻辑通信。
* **复用和分用：**
  * **复用 (Multiplexing)：** 发送方不同的应用进程都可以使用同一个传输层协议传送数据。
  * **分用 (Demultiplexing)：** 接收方的传输层在剥去报文首部后，能够把这些数据正确交付给目的应用进程。
* **差错检测：** 传输层不仅要对首部进行差错检测，还要对**数据部分**进行检错（网络层 IP 数据报只检验首部）。
* **提供两种不同的传输协议：** 即面向连接的 TCP 和无连接的 UDP。

**本质理解：**
IP 地址 = 找到主机；MAC 地址 = 找到网卡（物理链路下一跳）；**端口号 = 找到主机上的具体进程（如微信还是 QQ）。**

## 二、端口号与套接字 (Socket)

### 1. 端口号 (Port)
端口是传输层服务访问点 (SAP)，用于标识主机中的应用进程。端口号长度为 **16 位**（能表示 $0 \sim 65535$）。
* **熟知端口号 (Well-known Ports, 0~1023)：** 给 TCP/IP 最重要的一些应用程序使用。
  * **FTP：** 21 (控制连接)，20 (数据连接)
  * **TELNET：** 23
  * **SMTP：** 25
  * **DNS：** 53 (主要使用 UDP)
  * **HTTP：** 80
  * **HTTPS：** 443
* **登记端口号 (1024~49151)：** 供没有熟知端口号的应用程序使用。
* **客户端口号/短暂端口号 (49152~65535)：** 仅在客户进程运行时动态选择。

### 2. 套接字 (Socket)
在网络中采用发送方和接收方的套接字组合来识别端点。
$$套接字(Socket) = (IP地址 : 端口号)$$
**唯一标识：** 一个 TCP 连接由通信两端的套接字唯一确定，即四元组：(源 IP，源端口，目的 IP，目的端口)。

## 三、UDP 协议（用户数据报协议）

### 1. UDP 的核心特点
* **无连接：** 发送数据之前不需要建立连接，减少了开销和发送数据之前的时延。
* **尽最大努力交付：** 即不保证可靠交付（不保证顺序、不保证不丢失），主机不需要维持复杂的连接状态表。
* **面向报文（核心区分点）：** UDP 对应用层交下来的报文，**既不合并，也不拆分**，保留这些报文的边界。一次发送一个完整报文。
* **没有拥塞控制：** 网络出现拥塞不会使源主机的发送速率降低（适合实时会议、IP电话，允许丢包但不允许高延迟）。
* **首部开销小：** 只有 **8 字节**，比 TCP 的 20 字节首部短。

### 2. UDP 数据报格式与伪首部
UDP 首部共 8 字节，包含 4 个字段（各占 2 字节）：
* **源端口**、**目的端口**、**长度**（UDP 首部 + 数据的总长度）、**校验和**。
* **UDP 伪首部（408常考陷阱）：** 校验和计算时，会在 UDP 数据报前面临时增加 12 字节的伪首部（包含源 IP、目的 IP、协议号 17、UDP 长度）。**伪首部仅仅是为了计算校验和，不会向下传送给网络层。**

## 四、TCP 协议（传输控制协议）与报文段首部

### 1. TCP 的核心特点
* **面向连接：** 通信前必须先建立 TCP 连接（三次握手），通信结束后释放连接（四次挥手）。
* **点对点通信：** 每一条 TCP 连接只能有两个端点，不支持组播和广播。
* **提供可靠交付：** 通过 TCP 连接传送的数据，无差错、不丢失、不重复、并且按序到达。
* **全双工通信：** TCP 允许通信双方的应用进程在任何时候都能发送数据。两端都设有发送缓存和接收缓存。
* **面向字节流：** TCP 把应用程序交下来的数据仅看成一连串的无结构的**字节流**。不保留应用层报文的边界。

### 2. TCP 报文段首部格式（20 字节固定首部，重中之重）
* **源端口 (2B) 和 目的端口 (2B)**。
* **序号 (Sequence Number, 4B)：** TCP 是面向字节流的，本字段表示该报文段发送的数据的**第一个字节的序号**。
* **确认号 (Acknowledgment Number, 4B)：** 期望收到对方**下一个**报文段的第一个数据字节的序号。（若确认号为 $N$，表示序号 $N-1$ 为止的所有数据都已正确收到）。
* **数据偏移 (首部长度, 4位)：** 指出 TCP 报文段的数据起始处距离首部起始处的距离。**单位是 4 字节**。最大值为 15，故 TCP 首部最大 60 字节（20 字节固定 + 40 字节选项）。
* **六个控制位（核心标志）：**
  * **URG (紧急)：** 高优先级数据，配合紧急指针使用。
  * **ACK (确认)：** 建立连接后所有传送的报文段都必须把 ACK 置 1。
  * **PSH (推送)：** 接收方收到 PSH=1 的报文段，会尽快交付接收应用进程，不再等到整个缓存填满。
  * **RST (复位)：** 严重差错时释放连接，重新建立。
  * **SYN (同步)：** 用于建立连接时同步序号。SYN=1 且 ACK=0 为连接请求。
  * **FIN (终止)：** 用于释放连接。
* **窗口 (Window, 2B)：** **接收窗口 (rwnd)**，告诉发送方：“从本报文段首部中的确认号算起，接收方目前允许对方发送的数据量”。是流量控制的核心。
* **校验和 (2B)：** 同样需要加上伪首部（协议号改为 6）。

## 五、TCP 连接管理（建立与释放）

### 1. 三次握手（建立连接）
* **第一步 (SYN)：** 客户端发送连接请求报文。`SYN=1, seq=x`。（此时客户端进入 `SYN_SENT` 状态）。
* **第二步 (SYN+ACK)：** 服务器收到请求，同意连接。发送确认报文。`SYN=1, ACK=1, seq=y, ack=x+1`。（服务器进入 `SYN_RCVD` 状态）。
* **第三步 (ACK)：** 客户端收到确认后，再给服务器发出确认。`ACK=1, seq=x+1, ack=y+1`。（双方进入 `ESTABLISHED` 状态）。
  *(注：第三次握手的报文段**可以携带数据**，前两次不允许)。*

**为什么不能是两次握手？**
为了防止**已失效的连接请求报文段**突然又传送到了服务端，产生错误。服务端若直接建立连接并等待数据，将浪费极大的资源。

### 2. 四次挥手（释放连接）
* **第一步 (FIN)：** 客户端发完数据，发送连接释放报文。`FIN=1, seq=u`。（进入 `FIN_WAIT_1`）。
* **第二步 (ACK)：** 服务器收到并确认。`ACK=1, seq=v, ack=u+1`。（服务器进入 `CLOSE_WAIT`，客户端收到后进入 `FIN_WAIT_2`）。**此时处于半关闭状态，客户端不发数据了，但服务器若有数据仍可发送。**
* **第三步 (FIN+ACK)：** 服务器发完数据，发送释放报文。`FIN=1, ACK=1, seq=w, ack=u+1`。（进入 `LAST_ACK`）。
* **第四步 (ACK)：** 客户端收到后发送确认。`ACK=1, seq=u+1, ack=w+1`。（客户端进入 `TIME_WAIT`）。

**高频考点：为什么客户端在 TIME_WAIT 状态必须等待 2MSL（最长报文段寿命的两倍）？**
1. 保证客户端发送的最后一个 ACK 报文能够到达服务器。如果丢失，服务器会超时重传 FIN+ACK，客户端可以在 2MSL 内再次响应。
2. 防止“已失效的连接请求报文段”出现在本连接中。经过 2MSL，本连接持续的时间内产生的所有报文段都会从网络中消失。

## 六、TCP 可靠传输机制

TCP 保证可靠传输的核心机制包括：校验、序号、确认、重传。
* **累积确认：** 接收方不必对收到的分组逐个发送确认，而是对**按序到达的最后一个分组**发送确认。
* **超时重传 (RTO)：** TCP 采用自适应算法，利用 Jacobson 算法平滑计算往返时间 RTT，动态设定超时重传时间 RTO。
* **Karn 算法：** 在计算 RTT 时，只要报文段重传了，就**不采用**其往返时间样本（因为无法确认收到的是第一次发出的还是重传的应答）。

## 七、TCP 流量控制与拥塞控制（重难点区分）

### 1. 流量控制（端到端）
* **目的：** 解决发送方和接收方速率不匹配的问题（怕接收方缓存溢出）。
* **机制：** 基于**滑动窗口协议**。接收方通过 TCP 头部的**窗口字段 (rwnd)** 动态调整发送方的发送窗口大小。
* **发送窗口的上限：** $W = \min(rwnd, cwnd)$。即发送窗口不能超过接收方给出的窗口和拥塞窗口中的较小者。
* **零窗口探测：** 当接收方发送零窗口报文后，发送方启动持续计时器，超时后发送零窗口探测报文，防止死锁。

### 2. 拥塞控制（全局性）
* **目的：** 防止过多的数据注入到网络中，使网络中的路由器或链路不致过载。
* **拥塞窗口 (cwnd)：** 发送方根据自己估算的网络拥塞程度设置的窗口值。
* **慢开始门限 (ssthresh)：** 切换算法的阈值。

**四大算法（常结合使用）：**
1. **慢开始 (Slow Start)：** `cwnd` 初始为 1（通常为一个最大报文段 MSS）。每收到一个对新报文段的确认后，`cwnd` 翻倍（指数增长：1, 2, 4, 8...）。
2. **拥塞避免 (Congestion Avoidance)：** 当 `cwnd >= ssthresh` 时，改用拥塞避免算法。每经过一个 RTT，`cwnd` 加 1（加法增大，线性增长）。
   * **遇到超时（网络拥塞）的动作（Tahoe版）：**
     * `ssthresh` = 发生拥塞时发送窗口的一半（乘法减小）。
     * `cwnd` 重置为 1，重新开始慢开始。
3. **快重传 (Fast Retransmit)：** 接收方收到失序的报文段就立即发出重复确认。发送方只要**连续收到 3 个重复确认**（加上正常的1个，共4个ACK），就立即重传尚未收到的报文段，而不必等超时计时器。
4. **快恢复 (Fast Recovery，配合快重传，Reno版)：**
   * 发送方收到 3 个重复 ACK，知道只是丢包而非严重拥塞。
   * `ssthresh` = 发生丢包时窗口的一半。
   * `cwnd` = `ssthresh`（而不是 1）。然后直接进入**拥塞避免**（线性增长）。

## 八、408 经典计算与概念例题

### 题目 1：拥塞控制窗口计算
主机 A 向主机 B 建立一条 TCP 连接，最大段长 MSS 为 1KB，拥塞窗口 cwnd 初始值为 1KB，慢开始门限 ssthresh 为 16KB。若在发送第 12 个 RTT 后发生了超时事件，求第 14 个 RTT 发送时，cwnd 的大小。

### 解答步骤
1. RTT=1: cwnd=1
2. RTT=2: cwnd=2
3. RTT=3: cwnd=4
4. RTT=4: cwnd=8
5. RTT=5: cwnd=16 (到达 ssthresh，转为线性增长)
6. RTT=6: cwnd=17
7. ... 依次递增
8. RTT=12: cwnd = 16 + (12 - 5) = 23。此时发生超时。
**发生超时后的动作：**
* 新的 `ssthresh` = $\lfloor 23 / 2 \rfloor = 11\text{ KB}$。
* 新的 `cwnd` 回退到 1，重新慢开始。
**重新开始后：**
* RTT=13: cwnd=1
* RTT=14: cwnd=2
**答案：第 14 个 RTT 时，cwnd 大小为 2KB。**

### 题目 2：TCP 序号与确认号推演
主机甲发向主机乙发送了一个 TCP 报文段，包含 200 字节数据，序号 seq=500。求乙收到后回复的确认号是多少？
**解答：**
甲发送的数据占据了序号 500 到 699（共 200 个字节）。
乙正确收到后，期望甲下一次发送的数据从 700 开始。
因此，回复的确认报文段中，确认号 **ack = 700**。

## 九、首轮复习高频考法与陷阱防范

1. **陷阱：TCP 头部长度的单位**
   * IP 头部的“首部长度”字段单位是 4 字节，TCP 头部的“数据偏移”字段单位也是 **4 字节**。做题如果给出的二进制是 `0101` (即 5)，则首部长度是 20 字节。
2. **区分超时与 3 次重复 ACK 的惩罚力度**
   * **超时 (Timeout)：** 惩罚极重。说明网络非常拥堵，路由器队列满了，`cwnd` 直接**清 1**。
   * **3 次重复 ACK：** 惩罚较轻。说明网络还能传数据（否则收不到后续的 3 个包产生重复 ACK），只是偶尔掉包，执行快恢复，`cwnd` 减半。
3. **套接字与端口的区分**
   * 服务器的 Web 进程虽然只监听 80 端口，但如果同时连接了 10 万个客户端，操作系统会根据 `(源IP, 源端口, 目的IP, 目的端口)` 这个四元组套接字，区分并建立 10 万个**不同的 TCP 连接**，而不会混淆。
4. **面向字节流 vs 面向报文**
   * UDP 发送 10 次，接收方必然需要调用 10 次接收函数才能全部收完。
   * TCP 发送 10 次，每次 100 字节，接收方如果缓存足够大，可以一次性调用接收函数把 1000 字节全部读出。这是面向字节流的最直观体现。
